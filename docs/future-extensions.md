# 향후 확장 훅 포인트 (DESIGN.md §15)

MVP 범위 밖인 8개 항목이 지금 아키텍처의 어디에 연결되는지만 정리한다. 코드는 바꾸지
않는다 — 실제로 필요해질 때 아래 지점에서 확장하면 된다.

## 1. 카드사 API 연동 / 실시간 이벤트 수집

지금은 `backend/scripts/seed.py`가 `Benefit`/`PaymentEvent` 테이블을 정적 샘플로 채운다.
두 기능 모두 "그 채우는 방식"만 외부 API 폴링/웹훅으로 바꾸는 것이고, 데이터가 도착한
이후의 흐름(`app/repositories/benefit_repository.py`, `payment_event_repository.py`,
`app/services/rule_engine.py`)은 전혀 바뀌지 않는다. 레포지토리가 이미 저장 방식과
사용 방식을 분리해두고 있어서, 시딩 스크립트를 스케줄드 잡/웹훅 핸들러로 교체하기만
하면 된다.

## 2. OCR 영수증 인식 / 위치 기반 자동 추천

`/payment/recommend`는 이미 `merchant`/`category`/`amount`를 구조화된 입력으로 받는다
(`app/schemas/payment.py`의 `RecommendRequest`). 두 기능은 이 세 값을 사용자가 손으로
입력하는 대신 영수증 사진이나 GPS 위치로 자동 채우는 것뿐이라, 백엔드는 전혀 건드릴
필요가 없다 — 프론트엔드에 입력 경로 하나(카메라/위치 → 동일한 요청 payload)를
추가하면 된다.

## 3. 해외 결제(여행 국가별) 추천

`Benefit`/`PaymentEvent`에는 국가 구분이 없다. 실제로 필요해지면 두 테이블에 nullable
`country` 컬럼을 추가하고, `rule_engine.build_candidates()`의 매칭 조건에 국가 필터를
더하면 된다. 통화 단위(원화 고정 가정)도 이때 같이 손봐야 한다. 지금은 컬럼을 미리
추가하지 않는다 — 어떤 국가/통화 표현이 필요할지 실제 요구사항 없이 먼저 정하면
나중에 다시 바꿀 가능성이 크다.

## 4. 소비 패턴 기반 카드 추천 / 월간 절약 리포트 / 개인 맞춤 소비 분석

셋 다 누적된 이력 데이터가 있어야 의미가 생기는데, 지금 `payment_service.recommend_payment()`
는 완전히 stateless라 추천 결과를 저장하지 않는다. 세 기능 모두 같은 전제(과거 추천/결제
이력)가 필요하므로, 실제로 만들 때는:

- `app/routers/payment.py`의 `recommend()` 핸들러가 "추천 결과를 로그로 남기는" 지점이 된다.
- 로그 스키마(사용자별 추천 이력 테이블)는 지금 미리 설계하지 않는다. 어떤 지표
  (카드별 누적 절약액, 업종별 소비 빈도 등)가 실제로 필요한지 모르는 상태에서 스키마를
  정하면 나중에 다시 갈아엎을 가능성이 크기 때문이다.

이 셋은 "저장할 데이터가 없다"는 같은 이유로 미룬 것이지, 어렵거나 우선순위가 낮아서가
아니다 — 이력이 쌓이기 시작하는 시점이 곧 착수 시점이다.
